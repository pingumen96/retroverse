# Roadmap

Derived from `specification.md` §22 (milestones M0-M6) and `style.md` §27 (visual phases A-E), ordered by
technical risk. Each iteration ends with a verifiable gate; each work session delivers one verifiable step.

| Iteration | Scope | Gate |
|---|---|---|
| **I0** | M0 native foundations + style Phase A look-development and tooling | M0 Done (app starts, controllable camera, stable rendering, no engine) + Gate A (empty but credible room) |
| I1 | Risk spikes: FFmpeg decode to GL texture via PBO, RmlUi with gamepad navigation, emulator launch/return with fullscreen restore | Success criteria met or fallback recorded in an ADR |
| I2 | M1 ES-DE catalog (discovery, gamelist/media/es_systems parsing, SQLite + FTS5, stable IDs) + Windows launcher + `retroverse-cli` | M1 Done: reads a real ES-DE collection without moving ROMs, launches an emulator and returns |
| I3 | M2 SNES vertical slice: single-room generator and persistent WorldPlan (one cartridge per title with media, spine-out shelves and face-out displays), instanced cartridges with real covers in texture arrays, picking, inspect, play from the world, the hero CRT's video (one decoder), incremental update (with I2's step 13r: the catalog's refresh on the app's worker) | Gate B: already looks like the concept with one room; deterministic WorldPlan snapshot; NFR-08; 60 FPS at 1080p |
| I4 | M3 multi-room world: hub, room graph, PS1 room, theme packs, streaming, overrides/pins, map and teleport | Gate C: different rooms, same world |
| I5 | M4 screens and media: decoder scheduler, audio, CRT shader, playlists, fallbacks for missing videos | Every room has working TVs within the decoder budget |
| I6 | Arcade and handheld rooms | Gate D |
| I7 | M5 part 1: wizard, emulator management, settings, statistics, file watcher (games and media added in ES-DE appear without a restart), media coverage report per system | 30-minute controller-only session |
| I8 | Performance, Blender hero assets, license audit, golden screenshots, fault injection | Gate E + style §28 DoD |
| I9 | Installer, portable build, release | M5 Done |

Removed from scope: the integrated scraper (spec §10, FR-021 to FR-023). ES-DE stays the scraping tool; Retroverse
reads its metadata and media in place and uses generated labels and screenshots where media are missing (ADR-0003).

Deferred beyond v1: gamelist write-back, legacy EmulationStation/RetroBat/Batocera adapters, VR, hardware video
decoding, Linux, an OpenGL 3.3 fallback.

## I1: risk spikes (done)

Each spike delivers the first version of the module it de-risks, kept out of the app's main flow until a later
iteration wires it in, plus a measurement executable under `spikes/` with its own tests, a report in `docs/spikes/` and
an ADR in `docs/decisions/` (success criteria met, or the fallback taken). Every preset enables the vcpkg features
`video` (FFmpeg: avformat, avcodec, swscale, swresample; LGPL components only, linked as DLLs) and `ui` (RmlUi with
FreeType).

| Spike | Modules | Success criterion | Fallback | ADR |
|---|---|---|---|---|
| (c) Video on a texture | `rv_media` (FFmpeg demux and decode on a worker thread, a bounded frame queue, a presentation clock driven by timestamps), `gl::VideoTexture` (ring of persistently mapped PBOs freed by timestamp queries, fences as the fallback), `spikes/video` | Two 720p videos at 60 FPS for 60 s: p99 frame time at most 16.7 ms, upload under 2 ms, fewer than 1% late frames, drift within 2%, stable memory; a truncated or corrupt file falls back without a crash | YUV planes converted in the shader, 480p or a single decoder, prebuilt LGPL FFmpeg binaries pinned by SHA-256 | ADR-0004 |
| (d) Product UI | `rv_ui` (RmlUi 6.3 on SDL3 and OpenGL 3, backends vendored on our glad, an OFL font), `rv_ui_model` (navigation and focus from the action map), `spikes/ui` | A quick-catalog mock screen usable with the pad alone, stable focus, the UI pass under 1 ms, correct resizing | The product UI in Dear ImGui with gamepad navigation, behind C++ view models | ADR-0005 |
| (f) Return from the emulator | `rv_launcher` (Windows command-line quoting, waiting strategies, launch session state machine, outcome classification), the Win32 process runner and the window hand-over in `rv_platform`, a fake emulator, `spikes/launch` | 5 of 5 RetroArch launches back in the foreground, fullscreen, with pad input and 60 FPS within 1 s of the emulator's exit; wrappers wait for the process tree; crashes reported; never a kill | `AllowSetForegroundWindow` before the launch, a minimized window with a notification, a direct process with a "return" confirmation | ADR-0006 |

Outcomes (2026-10-16, reference machine; the spikes were measured while other agents were building, the video spike
once more after the merge with no other agent running; see each report):

- **(c) Video, adopted (ADR-0004):** FFmpeg software decoding on a thread per video, RGBA at most 720 rows, a pooled
  bounded queue, timestamp-driven presentation, a ring of 3 persistently mapped PBOs freed by `GL_TIMESTAMP` queries
  (fences stalled NVIDIA's threaded driver about 0.5 ms per upload). Two 720p30 clips in the second and third
  campaigns (the machine at most 58% busy): upload p99 1.1 to 1.4 ms, at most 0.22% of the frames late or dropped,
  drift 0.003%, flat memory (in the first campaign, 63 to 98% busy, one normal-priority run dropped 11.6% and one
  above-normal run drifted -4.80%); three real ES-DE videos (480p60 H.264): upload p99 about 0.4 ms. With no other
  agent running all 12 runs met every criterion at either priority; under other agents'
  builds, at normal priority, the 60 Hz frame pacing held up to about 46% machine load and failed from 51% (up to 5% of
  a real video's frames dropped), while 7 of 9 above-normal runs up to 70% met every criterion. I5 raises the process
  to above-normal priority while it renders and staggers 720p uploads (two due on one render frame reach 2.1 to 2.7 ms
  at p99). First frame on screen 7 to 20 ms after the start. Full 1080p uploads exceed 2 ms, hence the 720-row cap.
- **(d) Product UI, adopted (ADR-0005), criteria met in part:** RmlUi 6.3 runs the quick catalog with the pad alone (80
  scripted checks; text entry waits for the on-screen keyboard of I7), with a stable visible focus and correct resizing;
  the UI pass takes about 0.22 ms CPU and 0.11 ms GPU on quiet frames but 1.2 to 1.5 ms per held move and 3.0 to 4.2 ms
  per tap, accepted against the 16.7 ms frame (follow-up: a pooled vertex buffer). Navigation read its own binding
  table (`ui::NavBindings`), not yet the action map the table above plans for `rv_ui_model` (ADR-0005); I2 step 6
  moved it onto the action map.
- **(f) Emulator return, adopted (ADR-0006):** 30 of 30 isolated RetroArch launches came back in the foreground, in
  borderless fullscreen, with pad input and 60 FPS within 1 s of the exit (median about 74 ms); wrappers are followed
  through a job object, crashes are reported with their NTSTATUS name, nothing is ever terminated; the window is kept
  (not minimized) and `AttachThreadInput` brings the foreground back when another window holds it.

## I2: M1 ES-DE catalog and launcher (in progress)

## I3: M2 SNES vertical slice (planned)

M2 Done (specification §22): a real room generated from the data shows the cartridges of the system and stays stable
after an incremental import. Gate B (style §27, phase B): the room already looks like the concept although it is only
one room, built from the real data of an ES-DE library, with cartridges filled procedurally, a TV playing a local video,
the pickup and inspection of a cartridge, media and object fallbacks, the Balanced graphics profile and a benchmark; and
the WorldPlan snapshot is deterministic. The decisions are in
[ADR-0010](decisions/ADR-0010-world-generator-and-world-plan.md) (the generator and the WorldPlan),
[ADR-0011](decisions/ADR-0011-collection-rendering-and-cover-textures.md) (collection rendering and cover textures) and
[ADR-0012](decisions/ADR-0012-interaction-in-the-world.md) (picking, focus, inspection, the card, launching from the
world, the hero CRT); the facts behind them come from three read-only surveys of 2026-10-18: the documents
(requirements, the Gate B checklist, twenty conflicts between the documents), the code's readiness, and the reference
SNES collection (7,797 games; 1,535 with a cover, the scraped ones; 890 distinct titles among them, 727 of them USA
releases once deduplicated, 57 Europe only, 106 other; covers opaque 680 x 497 PNGs, 815 MiB; clips H.264 640 x 480 at
59.94 fps, already 4:3).

Decided before planning (the user and the orchestrator) and recorded in the ADRs:

- **One cartridge per title** among the SNES games that have media (890 of the 1,535 with a cover), the USA release
  preferred, then Europe, then other regions, by a defined title key and a deterministic choice; the other versions,
  hacks and unscraped games stay launchable from the quick catalog and are listed in the plan's `unplaced` with their
  reason (ADR-0010 §3).
- **Spines plus display cases, a compact room**: most cartridges stand spine-out and dense, the title on the spine; a
  few dozen stand face-out where the eye goes, chosen in priority order (favourites, then play count, then rating, then
  title): the 44 slots of the display cases and the featured wall shelf, and one face-out band at eye height across the
  hero wall's two modules (12 slots); the shelving is sized to the collection, as few spine-out modules as the titles
  and the reserve need, all full, the remaining sockets and walls given to decoration (shelf dressing, posters, the
  template's furniture), never empty or extra modules, so that the room never looks sparse; a library that fits the
  display slots and the band (G02's 50 titles) is all face-out; pointing at a spine-out cartridge pulls it out and
  shows its cover (ADR-0010 §3, ADR-0012 §3). On the reference library 56 titles stand face-out and 834 spine-out, in
  the two hero-wall modules and three side-wall modules.
- **Deterministic and incremental display**: a new title always enters the spine-out reserve next to its alphabetical
  predecessor and never reshuffles what stands; the face-out set changes only with an explicit regeneration (ADR-0010
  §3, §10).
- The **WorldPlan is a canonical JSON file** under `<user data>/worlds/<library id>/`; no database migration (schema v1
  closed at Gate M1); where-is is computed from the plan (ADR-0010 §9).
- Seeds and stable hashes use **SHA-256 of `rv_core`**, no new hash library; **no EnTT**; **no downloaded HDRI or
  texture**: the ambient light stays hemispheric with the ambient occlusion, and the Balanced profile of style §4.3 is
  the renderer as it is (one shadowed key light, ambient occlusion, sober bloom); Low and High are I8's.
- **One video decoder** in I3, SelectedGame on the hero CRT with the fallback chain to the cover and a test pattern; the
  scheduler, audio and playlists stay in I5 (ADR-0004, ADR-0012 §7).
- **Step 13r** (the catalog's refresh on the app's worker, with cancellation) is part of I3.
- Teleport and the map stay in I4; the quick catalog's card offers **"Mostra nella stanza"** (ADR-0012 §8).
- The user's covers and cartridge images are their own media, read at runtime, never in assets, fixtures or goldens:
  goldens and smoke tests use fixtures with generated covers and clips and invented titles and system names (no
  trademark in a committed image); the real room is checked through `scripts/real-library.ps1` (its data directory,
  plans and derived textures under `build/`) and the manual session. Automated tests never take the foreground.

### Gate B

`scripts/gate.ps1 -Gate B` runs Gate A's build matrix (no warning), the unit tests (the world's snapshot goldens and
property suites among them) and the GPU smoke tests in Debug and Release, the `[.bench]` cases and the benchmark in
Release, the goldens G01, G02, G02s, G06, G07, G08 (a and b) and G10 in both, prints the summary table (logs in
`build/gate-b`) and exits 1 when a step failed; all of it under `scripts/focus_watch.py`, as Gate M1 runs.
`-RealLibrary` adds, with ES-DE closed, `RV_LAUNCH_ALLOWLIST` set and empty, and snapshots before and after through
`scripts/real-library.ps1`, the real SNES room (the plan twice with one SHA-256, an incremental update after a second
import with 0 moves, covers cold and warm, the benchmark path), the refresh's p99 and NFR-01 with the room, and fails on
any difference. `docs/testing/gate-b.md` holds the figures, the map of requirements to proofs, style §24's minimum
result ("no interpenetrating shelf, console visible, video playable or correct fallback, room readable and navigable by
controller") and style §29's first expected result, the style §26.2 checklist answered for the goldens and for the real
room, and the manual session (the controller checklist of the approved plan's §7): pad only, in the real SNES room, a
title found in a display case and one on a spine-out shelf, pulled out, inspected, launched in RetroArch and back in
the same pose, the hero CRT playing its clip, "Mostra nella stanza" from the quick catalog, "Aggiorna libreria" with
nothing changed (0 moves), the media viewer; then the card's actions with keyboard and mouse. Gate B passes when the
script passes and the user signs the manual session and the verdict that the room already looks like the concept.
